# 样例的预期结果（手工推导）

这些结果是**按规则和制度原文手工算出来的**，不是跑代码跑出来的。
第 2 周实现引擎后，用它来对照——如果引擎输出与这里不同，先怀疑引擎，不要先改这里。

## 通用计算

| 项 | 公式 | 依据 |
| --- | --- | --- |
| 出差天数 | `return - departure + 1` | 项目假定，含两端（A-005） |
| 伙食补助费 | `天数 × 100`（西藏/青海/新疆 120） | 第十六、十七条 + 标准表（B/C 层） |
| 市内交通费 | `天数 × 80` | 第二十条 |
| 住宿限额 | 逐晚与 `limit_by_person_level[级别]` 比较 | 第十四条 + 71 号明细表 |

## SAMPLE-001　南京 3 天，司局级，合规

`2026-03-02` → `2026-03-04` = **3 天**，住 2 晚，每晚 450 元。

| 规则 | 输入 | 判断 | 结果 |
| --- | --- | --- | --- |
| R-REIMBURSE-UNIT-SCOPE | 中央单位 | 在允许集合内 | 通过 |
| R-REIMBURSE-OUTSIDE-STATION | 北京 → 南京市 | 不同城市 | 通过 |
| R-REIMBURSE-APPROVAL | approved=true | — | 通过 |
| R-REIMBURSE-VOUCHER | 审批单、车票、住宿发票齐 | — | 通过 |
| R-TRANSPORT-CLASS | 火车 / 二等座 / 司局级 | rank 3 ≤ 上限 5 | 通过 |
| R-LODGING-JS-CORE | 江苏·南京市，司局级，450/晚 | 450 ≤ 490 | 通过（2 晚） |
| R-LODGING-ROOM-TYPE | 标准间 / 司局级 | 531 号允许；497 号不分房型 | 通过（两者一致） |
| R-LODGING-NO-INVOICE | 住了，2 晚都有发票 | 不触发扣减 | 通过 |
| R-LODGING-PAYMENT-CARD | 公务卡 | — | 通过 |
| R-MEALS-ALLOWANCE | 3 天 × 100 = 300 | 申报 300 | 通过 |
| R-LOCAL-ALLOWANCE | 3 天 × 80 = 240 | 申报 240 | 通过 |
| R-LOCAL-MEETING-SCOPE | 一般出差 | 不触发 | 通过 |

**整体结论：通过。**

> 注意：住宿限额规则的检查项按 `person_level` 展开成 3 个，但本申请只用到「司局级」。
> 另外两个检查项（部级、其他人员）**未被触发**，这正是覆盖率要统计的东西。

## SAMPLE-002　南京 3 天，第一晚超限

`2026-04-10` → `2026-04-12` = 3 天，住 2 晚：**520 / 480**。

| 规则 | 判断 | 结果 |
| --- | --- | --- |
| R-LODGING-JS-CORE | 司局级限额 490。4-10 晚 520 > 490，4-11 晚 480 ≤ 490 | **不通过**（第 1 晚） |
| 其余 | 同 SAMPLE-001 | 通过 |

**整体结论：不通过。**

> 若按「总额 ÷ 晚数」判断：(520+480)/2 = 500 > 490，也判不通过——本例恰好结论相同。
> 换一组数字就能看出差别：**500 / 400 两晚，均价 450 合规，但第一晚超限**。
> 这是逐晚建模的理由（D-004）。

## SAMPLE-003　上海，缺一晚发票，级别未填

`2026-05-11` → `2026-05-13` = 3 天，住 2 晚，第二晚 `receipt_present: false`。

| 规则 | 判断 | 结果 |
| --- | --- | --- |
| R-LODGING-SH-001 | `person_level` 为 null | 信息不足 |
| R-LODGING-ROOM-TYPE | 同上 | 信息不足 |
| R-LODGING-PAYMENT-CARD | 第 2 晚付款方式为「其他」，但第 1 晚是公务卡 | 不通过 |
| **R-LODGING-NO-INVOICE** | 实际发生住宿 且 存在无发票的晚 | **不通过**，连带四项费用 |
| R-MEALS-ALLOWANCE / R-LOCAL-ALLOWANCE | 金额本身正确 | 通过，但受联动规则影响不得报销 |

**整体结论：不通过。**

> 这里能看出「联动规则」的实际效果：伙食费和市内交通费本身算得对，
> 但因为缺一张住宿发票，按第二十五条四项全不报。
> 只实现「扣住宿费」的版本会漏掉这个后果。

## SAMPLE-004　哈尔滨 8 月，旺季

`2026-08-10` → `2026-08-12` = 3 天，住 2 晚，每晚 **520**。司局级。

| 规则 | 判断 | 结果 |
| --- | --- | --- |
| R-LODGING-HLJ-HARBIN | 两晚日期都在 8 月，落进旺季 7–9 月，按旺季限额 **540** 判断：520 ≤ 540 | 通过 |
| （若误用淡季限额 450） | 520 > 450 | 会误判为不通过 |
| R-TRANSPORT-CLASS | 飞机 / 经济舱 / 司局级 | rank 1 ≤ 上限 1，通过 |
| R-LOCAL-MEETING-SCOPE | 学术会议，但举办方未统一安排食宿 → 条件不成立 | 通过 |
| R-MEALS-ALLOWANCE | 3 × 100 = 300 | 通过 |
| R-LOCAL-ALLOWANCE | 3 × 80 = 240 | 通过 |

**整体结论：通过。**

> 这是最能说明「为什么必须逐晚建模」的样例：如果只记录「住了 2 晚」，
> 无法判断是否落在 7 月 31 日跨到 8 月 1 日这种边界上。
