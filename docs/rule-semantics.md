# 规则匹配与展开语义

规则文件只描述「规定是什么」，本文规定「怎么用」。**引擎（第 2 周）必须严格按本文实现**，
否则同一份规则库会得出不同结果。

## 一、适用范围匹配

### 1.1 scope 的字段

```yaml
scope:
  province: 江苏            # 必填，与明细表「地区」列一致
  cities: [南京市, 苏州市]   # 可选，显式城市列表
  fallback: false           # 可选，true 表示「本省未列出的其他市县」
  person_level: [部级, 司局级]  # 可选，缺省表示三档都适用
```

### 1.2 三种写法及其含义

| 写法 | 含义 | 例子 |
| --- | --- | --- |
| `cities: [A, B]` | **枚举**：只匹配列出的城市 | 江苏「南京市、苏州市…」5 个市 |
| `fallback: true` | **兜底**：匹配本省所有未被其他规则列举的市县 | 江苏「其他地区」 |
| 两者都不写 | **全省**：匹配本省所有市县 | 北京「全市」、上海「全市」 |

> 「全市」在直辖市语境下等于「全省」，因为直辖市本身是省级行政区。**不要**把
> `cities: [全市]` 写成字面城市名——那会凭空造出一个叫「全市」的城市。

### 1.3 匹配优先级

同一份申请可能同时匹配多条规则的 scope（例如「其他地区」和「南京市」都能匹配南京市）。
**优先级按特异性，不按文件顺序**：

| 优先级 | 类型 | 分值 |
| --- | --- | --- |
| 1（最高） | `cities` 枚举命中 | 3 |
| 2 | 全省（两者都不写） | 2 |
| 3 | `fallback: true` | 1 |

取分值最高者。**同分且都命中 → 冲突**，输出 `需人工确认`，并在诊断层记录（第 3 周）。

> 为什么不用「文件里靠后的生效」：那样结果的正确性取决于 YAML 的书写顺序，
> 改一次排版就可能改变判定，而改动本身看起来无关紧要。这是隐式依赖，必须避免。
> 见 `docs/rule-decisions.md` D-005。

### 1.4 兜底的实现方式

`fallback` 的「其他」是本省**已列出的城市之外**，引擎需要：

1. 收集该省所有 `cities` 枚举规则里出现的城市，得到集合 S
2. 若申请城市 ∉ S 且存在 `fallback: true` 的规则 → 匹配它
3. 若申请城市 ∉ S 且**没有**兜底规则 → `制度未覆盖`（不是「通过」）

第 3 步是本项目的关键：**「没有规则」和「规则说可以」必须分开**。
设计上 `制度未覆盖` 是独立结果，不是 `不通过`，也不是 `通过`。

## 二、声明式冲突

有些规则在条文层面就互相矛盾（D-007 的房型、D-008 的会议市内交通）。这类不靠条件空间枚举发现，
而是**在规则里成对声明**：两条规则各自写 `conflict_with`，自检脚本检查关系是否双向。

### 2.1 运行期怎么处理

**不是「一命中就转人工」**，而是**看两者结论是否分歧**：

```
若两条规则都适用于本申请：
    分别计算结果
    若结论相同 → 按该结论输出
    若结论不同 → 需人工确认，并在结果的 conflict 字段里列出两条规则
若只有一条适用 → 按该条输出
```

例：司局级住标准间。531 号第十三条允许（通过），497 号第三条不分房型（通过）——
两者一致，判通过。但部级住标准间时，531 号要求普通套间（不通过），497 号放行（通过）——
分歧，转人工。

**如果写成「声明了冲突就永远转人工」，等于让两条规则互相抵消，正常情形也判不了。**

### 2.2 静态发现交给诊断层

`conflict_with` 只是**声明**。诊断层的任务是**不依赖声明**也能发现冲突——
否则规则库里漏写一处 `conflict_with`，冲突就永远不会被发现。

第 3 周的诊断层要求：**即使删掉所有 `conflict_with`，也必须能报出这两处冲突**。
这是它的验收标准之一。

## 三、检查项展开

规则是**编写与溯源的单位**（一条对应源表一行或一个条款），检查项是**执行与统计覆盖的单位**。
一条规则可能蕴含多个独立判断，若按规则统计覆盖，会出现「规则命中率 100%，
但某个阈值从没被测过」的假信号。

### 3.1 各类型的展开函数

| 规则类型 | 展开维度 | 展开数 | 检查项命名 |
| --- | --- | --- | --- |
| 住宿限额（base） | `person_level` | 3 | `{rule_id}::base::{level}` |
| 住宿限额（peak） | `person_level` | 3 | `{rule_id}::peak::{level}` |
| 交通等级 | `person_level × transport_type` | 3 × 4 = 12 | `{rule_id}::{level}::{transport_type}` |
| 伙食标准 | `区域档 × 事由` | 2 × 1 = 2 | `{rule_id}::{region_tier}` |
| 条件类（无发票、凭证、审批等） | 无维度 | 1 | `{rule_id}::main` |

> 条件类没有维度，因为它的判断对象是整份申请的某个标志，不是某个数值区间。
> **不是所有规则都能展开**，强行给条件类造维度只会让覆盖率数字失真。

### 3.2 覆盖率怎么算

```
覆盖率 = 被至少一个测试用例触发过的检查项数 / 检查项总数
```

分母是**检查项总数**，不是规则数。分类型分别报告，不合并成一个总数字——
合并会重新制造聚合掩盖的问题。

## 四、版本语义

### 4.1 两个不同的生效日

一条住宿费规则同时受两个时间约束：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `effective_from` / `effective_to` | **条款**的生效区间 | 531 号第十四条：2014-01-01 起 |
| `threshold_from` / `threshold_to` | **阈值**的来源文件生效区间 | 71 号明细表：2016-05-01 起 |

### 4.2 判定的顺序

```
if 申请出差日 not in [effective_from, effective_to]:
    → 本规则不适用（可能是上一版制度，或制度尚未施行）
elif 申请出差日 not in [threshold_from, threshold_to]:
    → 信息不足（制度有规定，但我们没有这一时段的阈值）
else:
    → 正常判定
```

**为什么用「出差日」而不是「报销日」**：制度约束的是出差行为发生的费用。
这条本身是建模假定，记在 `docs/ambiguity-log.md`。

### 4.3 覆盖边界（必须写进 README）

住宿费规则**只能覆盖 2016-05-01 之后**的申请：

- 2014-01-01 至 2015-12-31：531 号的附表我们没拿到（原文标注「略」）→ 无阈值可用
- 2016-01-01 至 2016-04-30：财行〔2015〕497 号的标准有原件，但本项目未录入 → 无阈值可用
- 2016-05-01 起：71 号明细表，已录入 6 个地区的子集 ✅

这是**真实的覆盖缺口**，不是疏忽。见 `docs/rule-decisions.md` D-013。

## 五、结果与合并

### 5.1 单条规则的输出

| 值 | 含义 | 什么时候用 |
| --- | --- | --- |
| `通过` | 条件满足 | 判定完成且未违反 |
| `不通过` | 能确定违反，且能说清违反了哪条 | 判定完成且违反 |
| `信息不足` | 输入缺失，或制度表述本身不足以判断 | 缺字段 / 无阈值 / 条款模糊 |
| `需人工确认` | 命中例外、跨版本、或规则冲突 | 逻辑上无法由程序定论 |
| `制度未覆盖` | 该事项现行制度没有规定，或我们没有对应规则 | 无规则命中 |

**`制度未覆盖` 不等于 `通过`。** 把二者混同会让漏洞伪装成合规。

### 5.2 汇总成整体结论

先汇总到**费用项**，再汇总到**整单**：

| 层级 | 规则 |
| --- | --- |
| 费用项 | 该费用项下所有检查项：任一 `不通过` → 不通过；否则任一 `需人工确认` → 需人工；否则任一 `信息不足` → 信息不足；否则任一 `制度未覆盖` → 未覆盖；全通过 → 通过 |
| 整单 | 按优先级取最严重：`不通过` > `需人工确认` > `信息不足` > `制度未覆盖` > `通过` |

严重度顺序的理由：**确定的坏消息优先于不确定的消息**。一份申请里只要有一项确定违规，
整体结论就该是不通过，不该因为另一项信息不足而含糊过去。

### 5.3 结果条目

每条检查结果必须带：

```json
{
  "check_item": "R-LODGING-JS-CORE::base::司局级",
  "rule_id": "R-LODGING-JS-CORE",
  "status": "通过",
  "observed": {"amount": 480, "limit": 490},
  "source": {"doc_no": "财行〔2013〕531号", "article": "第十四条", "table_ref": "..."},
  "message": "司局级住宿费 480 元/晚，未超过 490 元/晚的限额"
}
```

`source` 必须能从规则元数据直接带出——**这是「可追溯」的落地形式**，
也是第 5 周 citation precision 指标的天然素材。
