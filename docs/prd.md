# 需求文档（PRD 摘要）：差旅报销规则预检

> 这是一页摘要，不是完整 PRD。目的是说清「给谁解决什么问题、做到什么程度算完成」。
> 对应的实现与指标见 `docs/eval-report.md`、`docs/diagnosis-report.md`。

## 一、背景与问题

差旅报销的规则写在制度里，制度会修订，规则会漂移。实际工作中反复出现三类问题：

| 角色 | 遇到的问题 | 后果 |
| --- | --- | --- |
| 申请人 | 提交前不知道材料是否齐、金额是否超标 | 退回重提，来回沟通 |
| 审核人 | 同一份单据要逐条对照制度核对 | 效率低，且依赖个人经验 |
| 规则维护者 | 规则改过之后，没有人知道有没有两条打架、有没有情形没人管 | 问题在出事之后才被发现 |

**本项目只解决前两类中的「可自动判断」部分，并给第三类提供一个检查工具。**

## 二、用户与场景

### 用户 1：申请人

场景：出差结束后准备报销，提交前自查。

需要回答的问题：「我这份申请有没有明显问题？」「缺什么材料？」「我的住宿费超没超标？」

### 用户 2：规则维护者

场景：制度修订后更新规则库。

需要回答的问题：「改完之后规则库还有效吗？」「有没有两条规则在新旧版本下给出相反结论？」
「有没有哪种情形现在没有任何规则覆盖？」

> 审核人是第三类用户，但**本项目不提供审核工作台**——见第四节范围。

## 三、核心流程

```
申请人提交一份结构化申请
        ↓
规则引擎逐条检查（按版本、地区、人员级别筛选适用规则）
        ↓
每条检查项产出四种状态之一：
    通过 / 不通过 / 信息不足 / 需人工确认
        ↓
按费用类别汇总 → 整单结论
        ↓
申请人看到：哪一项有问题、依据哪一条、还缺什么
```

**关键设计：四种状态不能合并。**

- 「不通过」是确定的坏消息
- 「信息不足」是判不了，需要补充数据
- 「需人工确认」是规则之间有分歧，程序不该裁决

把后两者当成「不通过」会误伤；当成「通过」会漏检。

## 四、功能范围

### 做

| 功能 | 说明 |
| --- | --- |
| 规则检查 | 住宿、城市间交通、伙食、市内交通、报销凭证五类 |
| 版本判断 | 按出差日期选择适用制度版本 |
| 依据回溯 | 每条结论带文号、条款号、明细表行 |
| 规则库诊断 | 缺口、冲突、无效规则、覆盖度 |
| 制度问答 | 能算的直接算，要读的给引用，没规定的拒答 |

### 明确不做

| 不做 | 原因 |
| --- | --- |
| 发票 OCR | 是另一个技术问题，与「规则治理」这个目标无关 |
| 审批流 / 多级签批 | 属于流程系统，本项目只做单份单据的判断 |
| 与财务系统对接 | 需要真实系统权限，且不是能力证明的关键 |
| 前端界面 | 命令行足够验证流程；做 UI 会吃掉时间且不产生区分度 |
| 全量地区覆盖 | 只做 6 个地区子集，理由见 `docs/known-gaps.yaml` G-001 |

## 五、验收标准

**每条都能用一个可测的数字判断，不用「好用」「流畅」这类词。**

| 验收项 | 标准 | 当前 | 出处 |
| --- | --- | --- | --- |
| 规则可追溯 | 每条规则都能指回文号 + 条款号 | 34/34 | `docs/source-mapping.md`（脚本生成） |
| 规则库无未申报缺口 | 诊断报出的缺口数 | 0 | `docs/diagnosis-report.md` |
| 规则冲突可检出 | 已知两处冲突是否被自动发现 | 2/2 | 同上 |
| 检查项覆盖 | 被测试触发的检查项 / 总数 | 83/86（97%） | 同上 |
| 数值题正确率 | 50 条评测集中可计算类 | 85% | `docs/eval-report.md` |
| 路径准确率 | 三类分流是否正确 | 84%（区间 72–92%） | 同上 |
| 引用可核查 | 答案中的引用经三层校验的通过率 | 100% | 同上 |
| 空输入不误判 | 空申请产生的「通过」条数 | 0 | `tests/test_empty_claim.py` |

> 覆盖率 97% 里剩下的 3 个检查项是伙食补助费的西藏 / 青海 / 新疆档位，
> 不在测试覆盖的地区子集内，已登记为 G-005，不假装已解决。

## 六、风险与依赖

| 风险 | 影响 | 当前处理 |
| --- | --- | --- |
| **制度会修订** | 规则过期，判断失效 | 规则带版本与生效区间；有跨版本回归测试 |
| **数据来源层级不一** | 数值可信度不同 | 每个来源标 A/B/C 层级；B/C 级在答案里明确指出 |
| **只覆盖 6 个地区** | 其他地区判「制度未覆盖」 | 已登记 G-001；扩展需线性增加规则与测试 |
| **规则口径可能变** | 同一份规则在新旧制度下结论不同 | 不设优先级，冲突转人工，不替制度裁决 |
| **AI 回答可能无依据** | 误导用户 | 三层确定性校验；无依据时拒答，不猜 |

## 七、下一步（如果继续做）

按投入产出排：

1. **补 2014–2015 年的住宿费阈值**（当前判信息不足）——需要找财政部那一版附表
2. **扩大地区子集**——成本线性，价值取决于实际使用场景
3. **接入生成式模型**——抽取式答案可核查但不好读；接上后引用校验才会真正发挥作用
4. **审核人视角的批量复核**——当前只有单份判断，批量场景需要另做设计
