# travel-claim-rules

从公开的差旅费制度里提取可执行规则，判断报销申请，并**检查规则库自己**有没有缺口、冲突和无效规则。

附一个可核查的制度问答：能算的直接算，要读条文的给逐字引用，制度没规定的拒答。

```
Python 3.10+ · YAML 规则 · SQLite · 176 个测试 · MIT License
34 条规则 / 86 个检查项 / 72 条条文 / 50 条评测题
```

---

## 它能做什么

| 能力 | 输入 | 输出 |
| --- | --- | --- |
| **判断申请** | 一份结构化的报销申请（JSON） | 每个检查项的状态 + 依据（文号、条款号、明细表行） |
| **诊断规则库** | 无需输入，跑规则库自己 | 覆盖缺口、规则冲突、无效规则、检查项覆盖率 |
| **制度问答** | 一个自然语言问题 | 带引用的答案，或明确拒答 |

三件事共用同一套元数据：**文号、条款号、版本、生效日期**。规则里的每个数字都能指回它的出处。

### 判断结果的五种状态

| 状态 | 含义 |
| --- | --- |
| `通过` | 条件满足 |
| `不通过` | 能确定违反，且能说清违反了哪一条 |
| `信息不足` | 输入缺字段，或没有这个时段的阈值 |
| `需人工确认` | 命中例外、跨版本，或两条规则给出相反结论 |
| `制度未覆盖` | 规则库里根本没有管这件事的规则 |

**最后两种不能合并成「通过」**——否则规则库的缺口会被伪装成合规。这是整个项目的设计前提。

## 快速开始

```bash
git clone https://github.com/KINZHE/travel-claim-rules.git
cd travel-claim-rules

python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"

claimcheck items        # 应当输出「检查项总数: 86（规则 34 条）」
pytest -q               # 176 passed
```

用 conda 也行：`conda env create -f environment.yml && conda activate travel-claim-rules`。

> 安装后 `claimcheck` 命令在任何目录可用。它会自动向上找仓库根（含 `rules/` 与 `data/` 的目录），
> 也可以用环境变量 `CLAIMCHECK_ROOT` 显式指定。

## 演示

**判断一份申请**

```bash
claimcheck check data/samples/sample-002-over-limit.json
```

```
申请 SAMPLE-002  出差日 2026-04-10
>> [不通过] R-LODGING-JS-CORE
        2026-04-10 晚 520 元超过 限额 490 元
   [通过] R-MEALS-ALLOWANCE
        伙食补助费合计 300 元，与 3 天 × 100 元一致
   ...
按费用项:
  住宿费      不通过
  城市间交通费  通过
  伙食补助费   通过
  市内交通费   通过
整体结论: 不通过
```

注意它指出的是**哪一晚**超限、**限额多少**，不是笼统的「不通过」。

**按历史版本复核**

```bash
claimcheck check <claim.json> --as-of 2013-06-01
```

同一份申请在 2013 年按 2006 版制度判（公杂费 30 元/天），在现代按 2013 版判（市内交通费 80 元/天）。

**问制度**

```bash
claimcheck ask "南京出差，司局级，住宿最多能报多少？"
```

```
在江苏、南京市出差，司局级人员的住宿费限额为 490 元/人·天。

限额的单位是「元/人·天」，与住宿总额、天数要区分开。

财行〔2013〕531号 第十四条规定：出差人员应当在职务级别对应的住宿费标准限额内，...

依据：
  [表格] 财行〔2016〕71号 明细表 · 江苏省第1行：部级 900，司局级 490，其他人员 380
  [条款] 财行〔2013〕531号 第十四条

校验：通过
路径：compute | 规则 R-LODGING-JS-CORE
```

490 这个数字不是模型生成的，是从规则库读出来、能指回明细表行的。

**诊断规则库**

```bash
claimcheck diagnose
```

```
- 确定冲突 1 处（同字段、同类型的判断分歧）
- 疑似冲突 1 处（需人工判断）
- 缺口 0 处
- 无效规则 0 条
- 检查项覆盖 83/86（97%）
```

## 核心：规则库质量诊断

判断报销的项目很多，**检查规则库自己**的很少。这部分是本项目和同类项目的区别所在。

### 四类检查

| 检查 | 定义 | 现实后果 |
| --- | --- | --- |
| **缺口** | 条件空间里有输入组合不匹配任何规则 | 有些申请落进无人管辖的角落 |
| **冲突** | 某输入组合同时匹配两条结论不同的规则 | 同一份申请会因执行路径不同得出不同结论 |
| **无效规则** | 该规则在任何输入下都无法影响结论 | 维护者以为它在起作用，其实没有 |
| **覆盖度** | 哪些检查项从未被任何测试触发 | 测试全绿，但有规则从未被执行过 |

### 两处真实冲突（不是造出来的）

| 冲突 | 来源 | 检测级别 |
| --- | --- | --- |
| 房型 | 531 号第十三条「部级住普通套间」 vs 497 号第三条「不分房型」 | **确定**（同字段同类型） |
| 会议市内交通 | 第二十条「按天 80 元包干」 vs 第三十条「由举办方开支」 | **疑似**（一条禁止、一条放行） |

两份文件都现行有效，制度没有规定谁优先——所以系统**不自己选**，输出「需人工确认」。

**怎么证明检测不是读人工标注**：把规则里所有 `conflict_with` 声明删掉再跑，它仍然能发现。
这一条有测试守着。

### 冲突为什么分两级

按「结论不同」一刀切会大量误报：限额规则说通过、无发票规则说不通过，两条同时成立完全正常，
它们查的是金额和凭证两件事。

- **一级**：同类型 + 同判断字段 → 自动判定
- **二级**：一条禁止、一条放行 → 列为候选，需人工

二级刻意排除了联动规则和整单级准入检查，否则会有 4 条误报。

## 评测结果

50 条自建评测集（可计算 22 / 需读条文 22 / 拒答 6，其中版本陷阱 6、口语问法 24 条）。
**题目集已冻结**，分数来自首次运行，之后未针对失败题调整实现。

| 指标 | 结果 | 95% 置信区间 |
| --- | ---: | --- |
| 路径准确率 | 84% | 72–92% |
| 答案正确率 | 72% | 58–82% |
| 引用召回率 | 80% | 67–89% |
| 拒答正确率 | 90% | 79–96% |
| 版本正确率 | 100% | 93–100% |

### 阶梯消融：每个部件贡献多少

| 级别 | 加了什么 | 答案正确率 |
| --- | --- | ---: |
| L0 | 基线：全部走检索 | 30% |
| L1 | + 同义词映射 | 30% |
| L2 | + 版本过滤 | 40% |
| L3 | + 三类问题分流（能算的走规则引擎） | **72%** |

**L3 的 +32 个百分点是核心证据**：制度问答里数值类问题占相当比例，把它们交给检索 + 生成，
不如直接读已验证的规则。

**L1 零提升，如实记录**：查证过开关确实生效（5 道题的检索结果变了），但它不是当前瓶颈。

### 已知的短板（不掩饰）

- **拒答能力弱**：6 道拒答题只答对 1 道。系统没有「制度未覆盖」的通用判断，只靠一张关键词表。
  试过检索分数阈值和问句词汇覆盖率两条判据，**区间完全重叠，都不可分**。
- **引用校验捕获率是 0**：因为抽取式生成器不会编造，三层检查结构上不可能失败。
  它的价值要接上生成式模型后才体现。
- **两种上下文方式产出相同答案**：抽取式只能用一个片段，所以测不出「长上下文是否有用」，
  这一项标注为**未验证**。

完整报告见 [`docs/eval-report.md`](docs/eval-report.md)，方法见 [`docs/eval-design.md`](docs/eval-design.md)。

## 边界

这个项目明确不覆盖以下内容，**判不了就判不了，不猜**：

| 不覆盖 | 原因 | 当前行为 |
| --- | --- | --- |
| 6 个地区之外的住宿费 | 明细表有 36 个地区，只取了 6 个子集 | 判「制度未覆盖」 |
| 2014–2015 年的住宿费阈值 | 531 号附表原文标注「略」，未取得 | 判「信息不足」 |
| 发票 OCR、审批流、财务系统对接 | 超出「规则治理」这个目标 | 不做 |
| 伙食补助费的 A 级来源 | 只有地方政府与高校转载的数值 | 元数据标注来源层级 B |

制度原文、来源层级（A 官网原件 / B 政府转载 / C 商业法规库）与校验值见
[`sources/SOURCES.md`](sources/SOURCES.md)。申请数据全部是模拟数据，不含任何真实票据或个人信息。

## 架构

```
制度原文（5 份，含原始 xls 附件）
      │  按条切分，带版本元数据
      ▼
规则库（34 条 YAML）──┬── 质量诊断（缺口 / 冲突 / 无效 / 覆盖）
      │               │
      ▼               ▼
  引擎：版本门 → 范围匹配 → when 匹配 → 阈值门 → 求值 → 冲突判定 → 两层合并
      │
      ▼
  制度问答：分类 → 能算走引擎 / 要读走检索 / 没规定拒答 → 引用校验
```

| 模块 | 职责 |
| --- | --- |
| `model.py` | 规则与申请的数据结构、路径取值、派生值 |
| `checks.py` | 五类判断（阈值 / 枚举 / 等级序数 / 合计 / 布尔谓词） |
| `predicate.py` | 谓词求值，**三值逻辑**（真 / 假 / 未知） |
| `matcher.py` | 范围匹配与特异性优先级 |
| `engine.py` | 编排与结果合并 |
| `diagnose.py` | 质量诊断四项 |
| `corpus.py` / `retrieval.py` | 按条切分、字符二元组 + BM25 检索 |
| `qa.py` / `verify.py` | 问答编排、三层引用校验 |
| `evaluate.py` / `ablation.py` | 评测指标与阶梯消融 |

代码阅读地图（哪 12 处值得读）见 [`docs/code-map.md`](docs/code-map.md)。

## 常用命令

```bash
claimcheck check <claim.json> [--as-of YYYY-MM-DD] [--db runs.db --save] [--json]
claimcheck ask "..." [--context retrieve|full] [--as-of YYYY-MM-DD] [--json]
claimcheck diagnose [--out docs/diagnosis-report.md] [--strict]
claimcheck eval [--ablation] [--out docs/eval-report.md]
claimcheck items

python scripts/check_rules.py         # 规则自检：字段是否定义、条款是否真实、阈值是否与源表一致
python scripts/gen_source_mapping.py  # 由规则生成来源映射表（生成物）
python scripts/freeze_eval.py         # 核对评测题是否被改动
```

`diagnose --strict` 在有确定冲突、未申报缺口或无法复现的声明时返回非零，可直接做 CI 门禁。

## 明确不引入

这个清单和功能清单一样重要——它说明的是取舍。

| 不引入 | 理由 |
| --- | --- |
| OPA / Rego | 需要工具链、bundle 签名、SBOM 整套供应链，对这个规模是过度工程 |
| LangGraph / MCP | 流程是确定的几条线，不需要通用 agent 编排 |
| Langfuse / Phoenix | 观测平台按需用托管，不自建 |
| 前端框架 | 命令行足够验证流程 |
| 现成的规则引擎库 | 它们解决「执行规则」，本项目要解决「诊断规则库自身」，需要完全控制规则结构 |
| 向量数据库 / GraphRAG | 关键词检索是基线，是否引入由实验数据决定 |
